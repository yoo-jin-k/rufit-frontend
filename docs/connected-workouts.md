# 계정별 운동 연결과 저장 복구

`createConnectedWorkoutStorage(storage, session.scope)`는 확인된 서버/계정별로 편집 폼, 서버 운동 UUID, 로컬 수정 번호, 전송 준비 당시 원문과 요청, 마지막 저장 확인을 보관한다. 토큰을 저장하지 않는다. 현재 운동 화면에는 아직 이 컨트롤러를 연결하지 않았다.

## 사용 흐름

1. `link(session, remoteId)`로 실제 계정이 읽을 수 있는 진행 중 서버 운동을 확인한 뒤 폼을 만든다. 서버 세트의 연속된 종목 그룹과 휴식 대상을 로컬 ID로 연결한다. 같은 연결이 있으면 원본 폼을 유지한다. 기존 익명 로컬 기록을 가져오거나 새 서버 운동을 임의 생성하지 않는다.
2. `edit(remoteId, expectedRevision, form)`을 기다려 입력 저장을 확인한다. 빈 입력도 보관하고, 오래된 화면의 수정 번호는 거부한다. 네트워크 전송 중에도 폼 저장은 가능하다.
3. `queueLatest(remoteId, operationId)`는 유효한 전체 폼을 준비한 뒤 원문과 요청을 먼저 연결 저장소에 기록하고 outbox에 넣는다. 이전 요청이 있으면 같은 요청을 유지한다. 빈 입력은 blocked, 바뀐 입력이 없으면 idle, 기존 서버 충돌은 conflict다.
4. `flush(session)`는 계정과 연결 정보를 확인한 후 서버에 보낸다. 성공하면 로컬 확인을 기록한 다음에만 outbox에서 삭제한다. confirmedRevision과 서버 version만 진전시키고, 현재 폼을 이전 원문이나 서버 숫자 응답으로 교체하지 않는다.
5. 재시작 시 `recover()` 또는 `flush()`로 저장 단계의 중단을 복구한다. `revision > confirmedRevision`이면 전송 이후 더 편집한 내용이 남아 있다. 이전 요청을 정리한 뒤 최신 버전과 새 작업 ID로 다시 준비한다.

`list/load`는 저장된 폼과 pending/lastReceipt를 반환한다. `pending()`은 서버 충돌 사유가 있는 기존 outbox 항목을 확인한다. 다른 계정/서버는 다른 저장 키를 사용하며, 다른 scope의 세션은 네트워크 호출 전에 거부한다. 로그아웃한 세션은 새 HTTP 요청을 보내지 못한다.

## 중단과 실패 시 보존

| 중단 시점 | 남기는 데이터 | 복구 |
| --- | --- | --- |
| 연결 초안 저장 실패 | 최신 로컬 입력, 기존 연결 | 서버/대기에 새 요청을 넣지 않음 |
| 연결 초안 저장 후 outbox 저장 실패 | 원문·행 ID·같은 작업 ID/본문 | outbox를 다시 구성 |
| 서버 성공 후 로컬 확인 저장 실패 | 원문과 미확인 pending, outbox | 같은 요청 재생 후 확인 저장 |
| 로컬 확인 후 outbox 삭제 실패 | 확인된 버전과 pending, outbox | 같은 요청 재생, 확인 처리는 멱등 |
| outbox 삭제 후 연결 정리 실패 | 확인된 pending과 현재 입력 | 네트워크 없이 마지막 정리 |
| 서버 버전 충돌/확정 거절 | 현재 폼·준비 당시 원문·충돌 항목 | 자동 덮어쓰기/재전송 중지 |
| 손상 또는 원문/요청 불일치 | 저장된 원본 바이트 | 초기화하지 않고 오류 반환 |

outbox의 선택적 `beforeRemove(receipt)`는 대기 요청 삭제 전에 별도 폼/확인 정보를 영구 저장하는 훅이다. 이 훅이 실패하면 원래 요청을 유지한다. 훅 안에서 같은 outbox의 list/enqueue/flush를 다시 호출하면 직렬화 대기가 순환하므로 별도 폼 저장만 수행한다. 연결 컨트롤러가 이 순서를 관리한다.

## 계정 접속 시 복구 목록과 서버 재확인

`overview()`는 저장된 원문과 대기 요청을 읽어 상태·편집 가능 여부·다음 처리 종류를 반환한다. 네트워크, 파일 쓰기, 요청 복원/전송/삭제는 수행하지 않는다. 연결 원문이 없는 요청은 `unlinkedRequests`에 별도로 남긴다. 서로 다른 요청 본문이나 손상된 자료를 만나면 원문을 보존하고 오류를 반환한다.

| state | 의미 | nextAction |
| --- | --- | --- |
| `synced` | 현재 로컬 수정까지 서버 저장 확인 | `none` |
| `edited` | 아직 요청으로 준비하지 않은 입력 | `queue` |
| `blocked-input` | 빈칸 등 전송할 수 없는 입력 보존 | `fix-input`, 원인 `issues` 제공 |
| `pending` | 같은 작업 ID로 저장 결과 확인 필요 | `flush`, outbox 구성 전이면 `recover` |
| `conflict` | 확정 충돌 또는 종료 준비 이후 서버 변경 | `review` |
| `cleanup` | 저장 확인 또는 충돌 선택 후 로컬 정리 대기 | `flush` 또는 `recover` |
| `closing` | 종료·취소 요청 처리 결과 확인 필요 | `resume-close` |
| `closed` | 종료·취소된 기록과 입력 원문 보관 | `none`, 읽기 전용 |
| `remote-changed` | 대기 요청 없이 다른 기기의 수정 발견 | `review` |
| `remote-closed` | 대기 요청 없이 서버의 종료·취소 발견 | `review`, 명시적으로 보관 |
| `unavailable` | 서버에서 404/410 응답, 원문은 유지 | `none`, 자동 삭제/재연결 금지 |

`recheck(session, remoteId)`는 같은 계정의 활성 세션으로 **한 운동만 GET 조회**하고, 응답을 기다리는 동안 저장된 새 입력을 다시 읽어 반환한다. 폼·버전·요청·종료 상태를 자동 변경하지 않는다. 닫힌 기록은 서버에서 삭제되었어도 `closed`로 유지하면서 `remote.kind: unavailable`을 표시한다. 인증 만료·네트워크 오류·잘못된 응답은 호출자에게 오류로 전달하며 오프라인 `overview()` 자료는 그대로 남는다. 로그아웃한 세션은 새 조회와 진행 중 조회 결과 반환을 거절한다.

미확인 pending이 있으면 GET의 높은 버전만으로 성공이나 충돌을 단정하지 않는다. 자신의 저장 응답이 유실된 것일 수 있으므로 기존 `flush`의 동일 작업 ID 재시도로 영수증을 확인해야 한다. 조회 결과는 `remote.kind: advanced`와 기존 pending으로 반환한다. 재확인 자체는 재전송하지 않는다.

pending 없는 `remote-changed`는 두 원문을 비교한 후 `resolve`에 `operationId: null`, 확인한 서버 버전·로컬 수정 번호와 `keep-local` 또는 `use-server`를 넘긴다. 현재 버전보다 높은 서버 기록에만 허용되며 선택 전 서버/로컬이 다시 바뀌면 거절한다. 이전 입력은 backups에 남고 로컬 선택은 자동 전송하지 않는다.

반환된 `canEdit`/`nextAction`은 조회 시점의 화면 안내다. 영구 잠금이나 처리 실행을 뜻하지 않는다. 화면은 `canEdit`을 존중하고 편집에는 최신 수정 번호를, 충돌 선택에는 명시적 사용자 확인을 전달해야 한다. 닫힘·종료 처리·정리 대기·충돌 상태를 활성 폼으로 자동 복원하지 않는다. 실제 로그인 화면과 복구 목록 화면 연결은 아직 후속 작업이다.

## 충돌 선택과 원문 보관

`review(session, remoteId)`는 로컬 원문, 최신 서버 기록, 대기 요청을 읽기만 한다. 화면에서 두 기록을 비교한 후 `resolve(session, remoteId, decision)`을 호출한다. decision은 `expectedRevision`, `remoteVersion`, `operationId`, `choice`, `confirmed: true`가 필요하다. 요청 처리 전에 서버 버전을 다시 읽고 로컬 수정 번호도 확인하므로 비교 후 바뀐 기록에 오래된 선택을 적용하지 않는다.

| choice | 진행 결과 | 보관 |
| --- | --- | --- |
| `keep-local` | 원문/행 ID를 유지하고 확인한 서버 버전에 새 초안을 준비할 수 있음. 자동 전송하지 않음 | 이전 폼, pending, 저장 확인, 비교한 서버 기록 |
| `use-server` | 진행 중 서버 기록을 편집 폼으로 읽고 수정 번호를 진전시킴 | 버려지는 로컬 입력도 backups에 별도로 남김 |
| `archive` | 이미 끝났거나 취소된 서버 운동을 읽기 전용으로 표시 | 현재 원문과 미전송 요청도 보존 |

선택을 resolution에 먼저 저장하고 outbox에서 해당 요청을 제거한 다음 폼/백업/버전을 정리한다. 이 중 어떤 저장이 실패해도 `recover()`가 이어서 처리한다. 저장된 resolution은 폐기 의도이므로 해당 pending을 다시 enqueue하지 않는다. 처리 중에는 편집을 막는다. 정리 후 새 요청에는 새 UUID를 사용한다. 보관된 과거 요청이나 마지막 저장 확인의 작업 번호 재사용은 거부한다. 서버 저장 확인 후 대기 삭제가 실패하고 그 사이 서버가 다시 바뀐 경우도 같은 비교 절차로 처리한다.

서버 404/접근 불가로 비교할 수 없는 기록은 그대로 보존한다. 임의로 다른 운동과 연결하거나 자동 폐기하지 않는다. backups를 다시 운동으로 가져오거나 삭제/내보내는 UI는 아직 없다.

## 종료·취소와 응답 유실

`close(session, remoteId, expectedRevision, {action: 'finish' | 'cancel', confirmed: true, discardIncomplete: boolean})`는 최신 입력의 서버 저장이 확인되고 대기 요청이 없어야 한다. finish에는 완료 세트가 필요하며 미완료 세트를 제외하려면 명시적으로 `discardIncomplete: true`를 전달한다.

종료 요청을 closing에 먼저 보관한 뒤 서버를 읽는다. 서버가 진행 중이고 예상 버전이면 종료/취소한다. 응답 유실이나 로컬 종료 확인 저장 실패 후에는 `resumeClose(session, remoteId)`를 호출한다. 서버가 이미 끝났다면 그 상태만 보관하므로 종료 POST를 반복하지 않는다. 서버가 다른 버전의 진행 중 운동이면 conflict를 반환하고 편집을 막는다. 비교 후 `operationId: null`로 resolve해 로컬/서버 선택을 명시해야 종료 의도가 해제된다. 이 경우에도 이전 종료 의도와 원문을 백업한다.

`closed`에는 실제 서버의 종료/취소 결과를 저장한다. 현재 form은 완료 시 제외된 미완료 세트까지 원문 그대로 남긴다. **읽기/표시에서 form.workout.finishedAt만으로 활성 운동을 판정하지 말고 closed/closing/resolution을 먼저 확인해야 한다.** 컨트롤러의 edit/queueLatest는 닫힌 기록을 거부한다. offline recover는 저장된 정리 단계만 복구하며, closing의 실제 서버 확인은 로그인 후 resumeClose에서 수행한다.

저장 키는 기존 `rufit.connected-workouts.v1:`을 유지한다. schemaVersion 1을 읽고 다음 쓰기에 2로 기록한다. 버전 2를 모르는 구버전 앱은 이를 거부하므로 종료 정보를 무시하고 재편집할 수 없다. 알 수 없는 미래 버전/손상된 자료는 원문을 그대로 남긴다.

## 현재 범위와 주의점

- 하나의 저장소 어댑터 객체를 공유하는 같은 프로세스의 인스턴스를 직렬화한다. 서로 다른 브라우저 탭/프로세스/어댑터의 동시 편집 잠금은 별도 구현이 필요하다.
- 관리되는 계정의 queue/flush/recover는 이 컨트롤러를 통해 호출한다. 원문이 없는 기존 outbox 항목은 자동 전송하지 않는다. 대기 목록이 100개로 가득 찼다면 먼저 기존 요청을 처리하고 빈자리에 미전송 원문을 복구한다. 연결된 항목을 generic outbox.discard로 직접 지우면 원문과 정리 단계가 어긋나므로 사용하지 않는다.
- 충돌 선택과 종료/취소 복구는 컨트롤러까지 구현했다. 실제 로그인, 화면 구독, 비교/선택 화면 연결은 후속 단계다. 실제 모바일 자동 동기화 완료가 아니다. 보관 원문과 백업은 자동 정리하지 않으며 용량 관리 UI가 필요하다.
- 현재 로컬 기록 키는 수정하거나 자동 이전하지 않는다. 오프라인 운동을 신규 서버 기록으로 가져오거나 시작 시각을 바꾸지 않는다.
- 서버가 정규화한 종목 이름이나 만료된 휴식은 lastReceipt에서 확인할 수 있다. 늦은 응답으로 현재 입력을 자동 교체하지 않는다.

## 검증 (2026-09-13)

81개 자동 테스트 중 38개가 이 저장 복구 흐름을 검증한다. 계정/서버 분리, 느린 응답 중 편집, 단계별 디스크 실패, 빈값 보존, 오래된 수정 거절, 충돌, 손상, 응답 유실, 잘못된 성공 응답을 포함한다. 복구 목록에는 읽기 중 원문 불변, pending/정리 상태 구분, 재확인 중 새 입력과 로그아웃, GET 버전으로 저장 결과를 단정하지 않음, 연결 없는 요청, 다른 기기 수정·종료·404·410 검증을 추가했다.

실제 통합 시험은 전용 PostgreSQL과 서명 OIDC, 원자적 파일 교체 저장소를 사용한다. 서버 저장 응답을 지연하는 동안 빈칸과 메모를 다시 편집하고, 확인 파일 저장을 한 번 실패시킨다. 컨트롤러 재생성 후 동일 작업으로 재시도해 서버 버전이 한 번만 증가하는지, 최신 입력/로컬 세트 ID가 남는지 확인한다. 이어 유효해진 새 입력을 다음 서버 버전으로 저장하고 다른 계정 접근을 거부하는지도 확인한다. iOS/Android 실기기 강제 종료 시험은 별도다.

추가 실제 서버 시험: 다른 기기 역할의 요청으로 버전 충돌을 만들고 로컬 선택 뒤 outbox 삭제를 실패시킨다. 재생성 후 폐기된 요청이 복원되지 않고 새 UUID로만 다음 버전을 저장하는지 확인했다. 이어 미완료 제외 종료가 서버에서 성공한 후 로컬 확인 저장을 실패시켜 GET으로 복구했고, 취소 응답을 유실시켜도 POST 한 번으로 복구되는지 검증했다. 단위 시험에는 선택/삭제/마지막 정리와 종료 의도/응답/확인 저장 실패, 오래된 비교 거부, 원문 보관, schemaVersion 1 이전도 포함한다.

복구 목록의 실제 서버 시험은 파일 저장소를 재생성한 뒤 다른 기기의 변경을 GET으로 읽고, 전송 없이 로컬 버전·원문을 유지하는지 확인한다. 명시적 서버 선택 후 이전 메모 백업, 종료 응답 유실의 읽기 전용 안내, 삭제된 서버 기록의 원문 보관, 다른 계정 거절을 검증했다.
